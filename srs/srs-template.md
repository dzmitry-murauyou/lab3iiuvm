## 1. Введение

### 1.1 Назначение документа

Настоящий SRS определяет, **что** должна делать система KeyNest, а не как она будет реализована. Документ используется продуктовой командой (Заказчик и напарник), разработчиками (Java), QA, ревьюером по безопасности и преподавателем на протяжении всего курсового проекта: для согласования объёма, проектирования, написания тестов и приёмки релизов R1–R3. SRS опирается на бизнес-требования из [business-requirements.md](business-requirements.md) и на шаблон лабораторной работы №2; связанные артефакты — модель [sysml/keynest-model.sysml](sysml/keynest-model.sysml) и графические представления [sysml/keynest-views.sysml](sysml/keynest-views.sysml). Каждое требование имеет неизменяемый идентификатор `REQ-[AREA]-[NNN]` и проверяется согласно разделу 4.

### 1.2 Область применения продукта

**KeyNest v0.1** — новое **настольное (Desktop) приложение-менеджер паролей** для одного пользователя и одного устройства. Продукт генерирует надёжные пароли, хранит учётные данные в единственном локально зашифрованном файле `vault.knx`, позволяет структурировать записи по категориям, вести заметки, подставлять логин/пароль автозаполнением и работать с двухфакторной аутентификацией (TOTP). Бизнес-цель — прекратить хранение паролей в текстовых файлах и записках, ускорить ежедневный вход в сервисы и сохранить независимость от облачных сервисов.

**Входит в область действия:** разблокировка по мастер-паролю и 2FA; генерация паролей; CRUD-записей; категории, поиск, избранное; защищённые заметки; автозаполнение по горячей клавише; TOTP-коды; резервное копирование, импорт/экспорт; аудит слабых/повторных паролей; русско- и англоязычный интерфейс; работа без сети.

**Не входит (отложено):** облачная синхронизация и аккаунт, мобильные приложения, расширение для браузера, совместный доступ и передача паролей команде, биометрия и аппаратные ключи, платёжные данные, ИИ/МО-функции, поддержка macOS в релизе R1 (см. [2.6](#26-распределение-требований)).

### 1.3 Определения, акронимы и сокращения

| Term | Definition |
|------|------------|
| 2FA | Двухфакторная аутентификация; в KeyNest — мастер-пароль + TOTP-код или ключ восстановления |
| AES-256-GCM | Режим аутентифицированного шифрования, применяемый к записям хранилища |
| Argon2id | Функция выведения ключа (KDF) из мастер-пароля с защитой от перебора на GPU |
| BR | Business Requirement — бизнес-требование Заказчика (`BR-01`…`BR-10`) |
| HIBP | Have I Been Pwned / Pwned Passwords — внешний сервис проверки скомпрометированных паролей (k-анонимность) |
| KDF | Key Derivation Function — функция формирования ключа шифрования из пароля |
| MVP | Минимально жизнеспособный продукт; в проекте равен релизу R1 |
| REQ | Требование SRS с идентификатором `REQ-[AREA]-[NNN]` |
| SRS | Software Requirements Specification — настоящий документ |
| SysML v2 | Systems Modeling Language v2 — язык системного моделирования; текстовая нотация и метаданные используются для моделей и макетов GUI |
| TOTP | Time-based One-Time Password (RFC 6238), 6 цифр / 30 с |
| Автозаполнение | Подстановка логина и пароля в активное окно по глобальной горячей клавише |
| Запись | Одна карточка хранилища: название, логин, пароль, URL, категория, заметка, TOTP-секрет |
| Ключ восстановления | Одноразовый секрет, позволяющий восстановить доступ к хранилищу при утере 2FA |
| Мастер-пароль | Единственный пароль, которым открывается хранилище; не сохраняется на диске |
| Хранилище | Файл `vault.knx` со всеми зашифрованными записями пользователя |

## 2. Обзор продукта

### 2.1 Перспектива продукта

KeyNest — новый самостоятельный продукт, а не замена существующей системы. Владелец продукта — учебная команда проекта; Заказчик — Елена Соколова (руководитель офиса компании «Байт», 12 сотрудников, учебная легенда). Приложение работает целиком на компьютере пользователя: вышестоящих систем нет, нижестоящие — локальная файловая система, ОС (часы, буфер обмена, хранилище ключей) и две **опциональные** внешние службы (HIBP и GitHub Releases), отключённые по умолчанию. Гарантийного SLA и круглосуточной поддержки нет: модель поддержки — исправления в рамках курсового проекта, ревью напарника и демонстрация преподавателю. Диаграмма контекста: [img/context-diagram.png](img/context-diagram.png); формальная модель: [sysml/keynest-model.sysml](sysml/keynest-model.sysml).

### 2.2 Функции продукта

1. Создание и открытие локального зашифрованного хранилища по мастер-паролю + 2FA.
2. Генерация паролей с настраиваемой длиной 8–64, наборами символов и оценкой энтропии.
3. Ведение записей: логин, пароль, URL, категория, заметка, TOTP-секрет.
4. Категории, избранное, полнотекстовый поиск и фильтры.
5. Автозаполнение учётных данных по горячей клавише `Ctrl+Shift+K`.
6. Отображение TOTP-кодов и работа с ключом восстановления.
7. Резервная копия, восстановление, импорт CSV и экспорт зашифрованного JSON.
8. Аудит безопасности: слабые, повторно используемые, устаревшие и скомпрометированные пароли.
9. Русский и английский интерфейс, авто-блокировка и локальный журнал событий.

## 3. Требования

Общие соглашения: каждое требование имеет уникальный ID, формулировку с «должен/следует/может», обоснование, критерии приёмки и метод верификации (Test / Analysis / Inspection / Demonstration). Трассировка к бизнес-требованиям — через поле *More Information* и [приложение B](#5-приложения).

### 3.1 Внешние интерфейсы

#### 3.1.1 Пользовательские интерфейсы

**REQ-INT-001 — Четыре обязательных экрана.** Система должна предоставлять экраны: (1) разблокировки хранилища и 2FA, (2) главного окна хранилища, (3) редактирования записи и генератора паролей, (4) всплывающей панели автозаполнения. Общие элементы: строка поиска, горячие клавиши, состояния «пусто» и «ошибка», переключатель RU/EN, контраст по WCAG 2.1 AA. Минимальное разрешение — 1280×720. *Rationale:* единообразный и предсказуемый UI снижает число ошибок Заказчика. *Acceptance:* все 4 экрана открываются с клавиатуры, элементы имеют подписи, ошибки показываются в виде немодального уведомления. *Verification:* Inspection + Demonstration. *More Information:* BR-01…BR-07; макеты ниже.

#### 3.1.2 Аппаратные интерфейсы

**REQ-INT-002.** Система должна использовать только стандартную клавиатуру, мышь и системный буфер обмена; глобальная горячая клавиша `Ctrl+Shift+K` должна перехватываться без установки драйверов. Специализированное оборудование (токены, смарт-карты, сканеры отпечатков) в v1 не поддерживается. *Acceptance:* hotkey работает в Windows и Linux; при конфликте комбинации выводится понятное сообщение. *Verification:* Demonstration. *More Information:* BR-04; допущение A-06.

#### 3.1.3 Программные интерфейсы

**REQ-INT-003.** Система должна взаимодействовать с локальным хранилищем ключей ОС (Windows Credential Manager / libsecret) только для хранения обёрнутого ключа хранилища; мастер-пароль не должен туда передаваться. **REQ-INT-004.** При включённой проверке утечек система должна обращаться к Pwned Passwords API по HTTPS, передавая только первые 5 символов SHA-1-хэша (k-анонимность), с таймаутом 5 с и понятным сообщением при недоступности. **REQ-INT-005.** Проверка обновлений GitHub Releases должна быть отключаемой, не передавать данные хранилища и не блокировать запуск приложения. **REQ-INT-006.** Для TOTP система должна использовать системные часы ОС; расхождение > 30 с должно приводить к предупреждению. *Verification:* Test / Inspection. *More Information:* [img/context-diagram.png](img/context-diagram.png), BR-08…BR-10.

### 3.2 Функциональные требования

- **REQ-FUNC-001 | Разблокировка хранилища**
  - Statement: Система должна открывать файл `vault.knx` после ввода корректного мастер-пароля и предоставлять доступ к записям не более чем за 1,5 с при 1000 записях.
  - Rationale: BR-01 — единая точка доступа ко всем паролям.
  - Acceptance Criteria: верный пароль → главное окно; неверный → сообщение без раскрытия факта существования записей; счётчик попыток уменьшается.
  - Verification Method: Test
  - More Information: BR-01, [img/gui-unlock.png](img/gui-unlock.png).

- **REQ-FUNC-002 | 2FA и ключ восстановления**
  - Statement: Система должна поддерживать второй фактор при открытии хранилища (TOTP 6 цифр / 30 с, RFC 6238) и одноразовый ключ восстановления из 24 символов.
  - Rationale: BR-07 — защита при утечке мастер-пароля.
  - Acceptance Criteria: код принимается с допуском ±1 шаг; ключ восстановления принимается один раз и помечается использованным.
  - Verification Method: Test
  - More Information: BR-07, [img/gui-unlock.png](img/gui-unlock.png).

- **REQ-FUNC-003 | Генерация пароля**
  - Statement: Система должна генерировать пароль длиной 8–64 символа с независимыми переключателями `A-Z`, `a-z`, `0-9`, `!@#`, опцией исключения похожих символов и отображением оценки энтропии.
  - Rationale: BR-02 — заменить слабые придуманные пароли.
  - Acceptance Criteria: при длине 20 и всех наборах энтропия ≥ 100 бит; выключение всех наборов невозможно (минимум один активен); новый пароль при каждом нажатии.
  - Verification Method: Test
  - More Information: BR-02, [img/gui-record-editor.png](img/gui-record-editor.png).

- **REQ-FUNC-004 | CRUD записей**
  - Statement: Система должна позволять создавать, просматривать, изменять, удалять и помечать избранными записи с полями «название, логин, пароль, URL, категория, заметка, TOTP-секрет, дата изменения».
  - Rationale: BR-03 — базовая единица хранения.
  - Acceptance Criteria: после перезапуска данные идентичны; удаление требует подтверждения; поддерживается 1000 записей.
  - Verification Method: Test
  - More Information: BR-03, [img/gui-record-editor.png](img/gui-record-editor.png).

- **REQ-FUNC-005 | Категории**
  - Statement: Система должна поддерживать одноуровневый список категорий, назначение категории записи, фильтрацию по категории и счётчик записей в каждой категории.
  - Rationale: BR-05 — навигация по 100+ паролям.
  - Acceptance Criteria: удаление категории не удаляет записи (они переходят в «Без категории»).
  - Verification Method: Test
  - More Information: BR-05, [img/gui-vault.png](img/gui-vault.png).

- **REQ-FUNC-006 | Поиск и фильтры**
  - Statement: Система должна искать записи по названию, логину, URL и заметке без учёта регистра, а также фильтровать по категории, избранному и недавно изменённым.
  - Rationale: BR-05 — экономия времени при входе.
  - Acceptance Criteria: результат за ≤ 200 мс на 1000 записей; пустой результат показывает подсказку, а не ошибку.
  - Verification Method: Test
  - More Information: BR-05, REQ-PERF-002.

- **REQ-FUNC-007 | Защищённые заметки**
  - Statement: Система должна хранить произвольный текст заметки до 2000 символов в записи, шифруя его так же, как пароль.
  - Rationale: BR-06 — Заказчик хранит подсказки и коды восстановления рядом с записью.
  - Acceptance Criteria: заметка не видна в несвязанной записи и не попадает в открытом виде в файл хранилища.
  - Verification Method: Test + Analysis
  - More Information: BR-06, [img/gui-vault.png](img/gui-vault.png).

- **REQ-FUNC-008 | Автозаполнение**
  - Statement: При нажатии `Ctrl+Shift+K` система должна определить активное окно/домен, предложить подходящие записи и подставить логин и пароль в поля формы или поместить их в буфер обмена.
  - Rationale: BR-04 — ускорить ежедневный вход и исключить перепечатывание.
  - Acceptance Criteria: панель появляется ≤ 2 с; при нескольких совпадениях показывается список; после подстановки буфер очищается через 30 с.
  - Verification Method: Demonstration
  - More Information: BR-04, [img/gui-autofill.png](img/gui-autofill.png), REQ-POC-001.

- **REQ-FUNC-009 | TOTP-коды записей**
  - Statement: Система должна вычислять и отображать 6-значные TOTP-коды для записей с секретом, показывая оставшееся время действия кода.
  - Rationale: BR-07 — второй фактор для внешних сервисов без отдельного приложения.
  - Acceptance Criteria: код совпадает с эталонным генератором RFC 6238 при одинаковом времени; обновляется каждые 30 с.
  - Verification Method: Test
  - More Information: BR-07, [img/gui-vault.png](img/gui-vault.png).

- **REQ-FUNC-010 | Резервная копия и восстановление**
  - Statement: Система должна создавать зашифрованную резервную копию хранилища по требованию пользователя и восстанавливать хранилище из копии после ввода мастер-пароля.
  - Rationale: BR-08 — защита от потери файла.
  - Acceptance Criteria: восстановленная копия побайтово эквивалентна по набору записей; повреждённая копия отвергается без потери текущего хранилища.
  - Verification Method: Test
  - More Information: BR-08, REQ-REL-002.

- **REQ-FUNC-011 | Импорт и экспорт**
  - Statement: Система должна импортировать CSV KeePass/Bitwarden и экспортировать хранилище в зашифрованный JSON; обе операции должны требовать повторного ввода мастер-пароля.
  - Rationale: BR-08 — перенос между устройствами без облака.
  - Acceptance Criteria: импорт 1000 строк завершается отчётом о пропущенных строках; экспорт не содержит открытых паролей.
  - Verification Method: Test
  - More Information: BR-08, REQ-DIST-001.

- **REQ-FUNC-012 | Аудит безопасности**
  - Statement: Система должна формировать отчёт о слабых (< 40 бит энтропии), повторно используемых и устаревших (> 180 дней) паролях и опционально проверять их через HIBP.
  - Rationale: BR-09 — избавиться от повторных паролей.
  - Acceptance Criteria: отчёт содержит ID записи и тип проблемы; сетевая проверка выполняется только после явного согласия.
  - Verification Method: Test
  - More Information: BR-09, REQ-SEC-007.

### 3.3 Качество обслуживания

#### 3.3.1 Производительность

- **REQ-PERF-001** — Разблокировка хранилища с 1000 записей должна занимать ≤ 1,5 с на эталонной машине (4 ГБ ОЗУ, HDD, Java 17). Критерий: 95-й перцентиль по 20 запускам.
- **REQ-PERF-002** — Поиск и фильтрация по 1000 записей должны выполняться ≤ 200 мс. Критерий: замер в JUnit-тесте с фикстурой.
- **REQ-PERF-003** — Панель автозаполнения должна появляться ≤ 2 с; потребление ОЗУ в простое ≤ 350 МБ. Критерий: демонстрация + JMeter/VisualVM-профиль.

#### 3.3.2 Безопасность

- **REQ-SEC-001** — Ключ шифрования должен выводиться из мастер-пароля функцией Argon2id (память 64 МиБ, 3 итерации, 4 потока, соль 16 байт). Критерий: сверка параметров с RFC 9106, Unit-тест.
- **REQ-SEC-002** — Записи должны шифроваться AES-256-GCM с уникальным nonce на запись и аутентифицированным заголовком файла. Критерий: изменение одного байта файла приводит к отказу аутентификации.
- **REQ-SEC-003** — Мастер-пароль должен быть не короче 12 символов; восстановление без ключа восстановления невозможно. Критерий: негативные тесты.
- **REQ-SEC-004** — После 5 неудачных попыток ввода система должна вводить задержку 30 с и не раскрывать, какой из факторов неверен. Критерий: тест сценария.
- **REQ-SEC-005** — Скопированный пароль должен автоматически удаляться из буфера обмена через 30 с; пароли и TOTP-секреты не должны попадать в логи, телеметрию и сообщения об ошибках. Критерий: инспекция логов и тест буфера.
- **REQ-SEC-006** — Хранилище должно блокироваться через 5 минут простоя, при сворачивании окна и при блокировке экрана ОС. Критерий: демонстрация трёх сценариев.
- **REQ-SEC-007** — При проверке утечек наружу должны передаваться только первые 5 символов SHA-1-хэша пароля; сам пароль не должен покидать устройство. Критерий: анализ трафика (mitmproxy/лог запроса).
- **REQ-SEC-008** — Система должна проверять целостность заголовка и версию формата файла и обнулять временные буферы с ключами после использования. Критерий: code review + негативные тесты.

#### 3.3.3 Надёжность

- **REQ-REL-001** — Сохранение должно быть атомарным: запись во временный файл, `fsync`, затем атомарная замена; при сбое предыдущая версия файла остаётся доступной. Критерий: тест с прерыванием процесса.
- **REQ-REL-002** — Восстановление из резервной копии должно быть идемпотентным и не должно портить текущий файл при ошибке. Критерий: повторное восстановление даёт тот же результат.

#### 3.3.4 Доступность

- **REQ-AVAIL-001** — Все функции R1–R2 должны быть доступны без сетевого подключения; недоступность HIBP/GitHub не должна блокировать запуск, поиск и автозаполнение. Критерий: тест с отключённым сетевым интерфейсом (≥ 99 % операций успешны в офлайне).

#### 3.3.5 Наблюдаемость

- **REQ-OBS-001** — Система должна вести локальный журнал событий (вход, блокировка, изменение/удаление записи, экспорт, ошибки) объёмом до 500 событий с возможностью выгрузки; журнал не должен содержать секретов.
- **REQ-OBS-002** — Сообщения об ошибках должны быть понятны пользователю, содержать код события и не содержать стек-трейсов с конфиденциальными данными; стеки пишутся только в локальный файл диагностики по явной команде.

### 3.4 Соответствие стандартам

- **REQ-COMP-001** — Реализация криптографии и 2FA должна соответствовать RFC 6238 (TOTP), RFC 9106 (Argon2id) и рекомендациям NIST SP 800-63B по парольным политикам; применение самописных криптоалгоритмов запрещено.
- **REQ-COMP-002** — Форма и идентификация требований должны соответствовать ISO/IEC/IEEE 29148:2018 и шаблону REF-01; каждый тест должен ссылаться на ID требования.
- **REQ-COMP-003** — Собственный код распространяется под лицензией MIT; зависимости должны иметь совместимые открытые лицензии и перечисляться в `NOTICE.md`; UI должен удовлетворять WCAG 2.1 AA по контрасту и управлению с клавиатуры.

### 3.5 Проектирование и реализация

#### 3.5.1 Установка

**REQ-INST-001.** Приложение должно поставляться установщиками `jpackage` для Windows (MSI) и Linux (DEB/RPM) со встроенной средой исполнения Java 17; установка не должна требовать прав администратора и не должна изменять системный реестр кроме записей удаления. Удаление должно оставлять файл хранилища нетронутым.

#### 3.5.2 Сборка и поставка

**REQ-BUILD-001.** Сборка должна выполняться командой `mvn verify`, быть воспроизводимой (зафиксированные версии зависимостей), включать JUnit 5-тесты, генерацию контрольной суммы артефакта и семантическое версионирование `MAJOR.MINOR.PATCH`.

#### 3.5.3 Распределение

**REQ-DIST-001.** Топология — один пользователь, одно устройство, один файл хранилища; перенос данных между устройствами выполняется вручную через зашифрованный экспорт (REQ-FUNC-011). Серверная часть, репликация и облачная синхронизация в v1 запрещены.

#### 3.5.4 Сопровождаемость

**REQ-MAINT-001.** Код должен быть разделён на слои `ui / service / crypto / storage` без циклических зависимостей; публичные методы сервисного слоя должны иметь Javadoc; покрытие тестами сервисного слоя — не менее 60 %; изменения проходят ревью напарника через pull request.

#### 3.5.5 Повторное использование

**REQ-REUSE-001.** Модули `CryptoService`, `PasswordGenerator`, `TotpService` и `EncryptedStorage` должны быть независимыми (без зависимостей от JavaFX) и иметь стабильные интерфейсы, чтобы их можно было переиспользовать в будущих CLI-/мобильных версиях.

#### 3.5.6 Переносимость

**REQ-PORT-001.** Приложение должно работать на Windows 10/11 и Linux x86_64 без изменения исходного кода; платформенно-зависимый код (горячие клавиши, хранилище ключей) должен быть вынесен за интерфейс; macOS является отложенной целью (R3+).

#### 3.5.7 Стоимость

**REQ-COST-001.** Совокупные денежные затраты на инфраструктуру и лицензии должны быть равны 0 BYN: используются только ноутбук студента, локальная ФС, GitHub и бесплатные Java-библиотеки. Платные облачные сервисы и лицензии не допускаются.

#### 3.5.8 Сроки

**REQ-DEAD-001.** Проект должен быть реализован тремя инкрементами в течение учебного семестра 2026/2027: R1 — 4-я неделя (MVP), R2 — 9-я неделя (безопасность), R3 — 15-я неделя (качество и защита). Конкретные календарные даты уточняются преподавателем (допущение A-08). Критерий готовности каждого инкремента — зелёная матрица верификации раздела 4.

#### 3.5.9 Доказательство концепции

**REQ-POC-001.** До начала R1 должен быть выполнен PoC «Глобальная горячая клавиша + буфер обмена» на Windows и Linux (таймбокс — 1 неделя). Успех: панель предлагает запись и подставляет данные в тестовую форму ≤ 2 с; при провале включается резервный сценарий A-06 и пересматривается REQ-FUNC-008.

#### 3.5.10 Управление изменениями

**REQ-CM-001.** Идентификаторы BR и REQ неизменяемы; изменение формулировки увеличивает суффикс версии (`REQ-FUNC-008-V2`) и отражается в истории изменений. Каждый релиз сопровождается `CHANGELOG.md`, списком затронутых требований и инструкцией миграции формата `vault.knx`; ломающие изменения формата файла требуют автоматической конвертации с резервной копией.

### 3.6 ИИ/МО

**Не применимо.** KeyNest v0.1 не содержит моделей машинного обучения и не принимает решений на основе данных: генерация паролей использует криптографически стойкий ГПСЧ, а аудит основан на детерминированных правилах. Разделы 3.6.1–3.6.6 оставлены пустыми для совместимости с шаблоном REF-01; при добавлении ML-функций (например, скоринга паролей) будут заведены требования с областью `ML` и описаны данные, ограничители, этика, human-in-the-loop и жизненный цикл модели.

### Приложение C. Бизнес-правила (кратко)

BR-RULE-01 — мастер-пароль ≥ 12 символов; BR-RULE-02 — ключ восстановления 24 символа, одноразовый; BR-RULE-03 — авто-блокировка 5 мин; BR-RULE-04 — очистка буфера 30 с; BR-RULE-05 — 5 неудачных попыток → задержка 30 с; BR-RULE-06 — категории одного уровня; BR-RULE-07 — один TOTP-секрет на запись; BR-RULE-08 — экспорт/импорт требует повторного ввода мастер-пароля; BR-RULE-09 — сеть только по явному согласию; BR-RULE-10 — заметка ≤ 2000 символов. Полный список — [business-requirements.md](business-requirements.md).

### Приложение D. Открытые вопросы и отложенные требования

3. Поддержка macOS, биометрии, FIDO2, браузерного расширения и облачной синхронизации вынесена за рамки v0.1.
4. Решение о ML-скоринге паролей принимается после R3; при положительном решении заполняется раздел 3.6.
